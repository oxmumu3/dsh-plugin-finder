# 从一个需求到插件第一次用成

2026-10-20，在隔离的 DSH `0.2.1-rc.2` 测试环境实跑。材料是合成 Markdown，没有使用真实业务文件。这是一条开发验收案例，不是外部用户采用或增长结果。

## 需求与发现

输入没有给插件名：

> 我想在 DSH 右侧预览本地 Markdown 里的 Mermaid 流程图和 KaTeX 数学公式。工作区有一份合成文件 plugin-discovery-demo.md，请找合适的插件，说明需要什么环境、怎么开始，先不要修改文件。

宿主默认模型理解出文件读取、Mermaid、KaTeX 与右侧预览四项能力，保留用户约束“先不要修改文件”。随后动态搜索第三方 Awesome 索引和 GitHub topic，用户原生市场未配置；读取排序靠前的作者资料后，将 `dsh-md-studio@1.2.0` 推荐为单插件方案。它不在旧版固定 15 条集合中。

本次读取到 Awesome format-1 索引 3112 条、GitHub 查询返回 1 个仓库，最终交给模型 6 个候选。这些是来源与检索计数，不能解释为质量、使用量或已核验插件数。npm 和 Git 对同版本的安装来源存在冲突，界面保留了提示；本次只选择精确 npm 版本。

两次模型调用的单次观察耗时分别约 4.3 秒与 31.1 秒。不是性能基准或平均值，网络与模型状态变化会影响时间。

## 安装与第一次使用

1. 从推荐卡片进入 DSH 原生插件页，填写精确 npm 来源 `dsh-md-studio@1.2.0`，由宿主完成安装并启用。
2. 读回已安装版本及客户端文件 SHA-256，和独立检查的发布包一致；未将 Git README 当成 npm 包的实际代码。
3. 选择 `sample-workspace`，方案进入原生会话输入框。读回包含原始需求、精确插件来源及限制的 4477 字草稿，没有自动发送消息。
4. 通过原生右侧文件浏览器只读打开合成文件。Mermaid 从源码变成包含“需求”“方案”两个正确节点的 SVG；切到源码再返回图形正常。
5. 两个 KaTeX 公式继续显示。安装前原生 DSH 已能显示这两个公式，所以本例的功能增量是 Mermaid 图形与查看交互，不能把 KaTeX 算成新增能力。
6. 通过 Finder 界面主动保存一条明确标注“开发验收合成任务”的本机反馈，并从原生存储读回。没有创建公开 Issue 或联系作者。

精确安装依据：[npm 1.2.0 清单](https://registry.npmjs.org/dsh-md-studio/1.2.0)。本次 tarball SHA-256 为 `93a268fddcb7866f1641ea49ecb2b9a90ccc63557a55a484827291509f6715ca`，已安装客户端 SHA-256 为 `da90ace1981a6478d38a9ec583b281344dd17c3f89c1998a0a8bb6bc6e2115ef`。

## 安装后怎么继续

实际重启宿主后，Finder 从本机存储恢复了原始需求、6 个候选及同一方案，没有重新调用模型。随后以这份真实保存的合成任务作为回归材料，核对已有草稿保护：宿主返回 `preserved`，点击「打开已有草稿」进入准确的原会话，读回测试文字没有变化。点击「新需求」后，bootstrap 不再返回 workflow；通过原生侧栏回到同一会话，草稿仍完整保留。上述回归没有发送会话消息。

## 能证明什么

这条案例证明：任务中不先说插件名，也能从外部变化的供给找到一个未预置候选，阅读资料、给出方案、通过原生管理器安装、把方案交接到指定工作区，并完成一次可观察的功能任务。

它没有证明所有推荐都正确、所有候选兼容、自动安装、复杂插件组合有效，或外部用户留存与创作者增长。当前也不会自动读取安装状态或回收后续会话结果；重启恢复、草稿保护、最终公开安装包的独立验收列在本版 [Release 记录](https://github.com/oxmumu3/dsh-plugin-finder/releases/tag/v0.2.0-preview.1)。增量价值还需按[两天对照实验](experiment.md)比较。
