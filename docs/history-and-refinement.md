# 我的方案与反馈优化验收

日期：2026-10-20。版本：`0.2.1-preview.2`。

## 修复的问题

原交互稿已经包含「我的方案」和历史回看，但实际 `0.2.0-preview.1` 只保留一个 current，且「新需求」会删除它。本次修复落实原设计，不将历史保存包装成临时新增需求。

- 「找方案 / 我的方案」内部导航始终可达；新需求只清活动指针，旧任务继续保存。
- 理解和推荐均保存为历史版本；反馈关联精确任务、版本，优化后仍能回看旧方案。
- 会话关联保存精确工作区与会话 ID；继续只打开原会话，不创建会话、不注入或发送草稿。
- 单任务 JSON 可导出、导入；导入不替换当前编辑内容，重复导入幂等。
- 旧域不改版本或表结构，新历史使用独立域；缺失或过期任务身份拒绝写入，不静默写入别的任务。

## 已观察的本机结果

在正在使用的官方 Desktop `0.2.1-rc.2`、原有 desktop profile 中，经原生插件页卸载旧 Finder、安装并启用本版。只更新 Finder，应用主进程与 Host 进程保持不变。

真实资料库试跑的旧推荐已从本轮 checkpoint 恢复，保留原搜索时间、原始需求、候选作者资料及原方案。恢复来源明确可见；原 checkpoint 不含会话 ID，操作者另行只读核对原会话和工作区，再在恢复备份中重新关联，不能声称关联由旧记录自动恢复。旧版无任务 ID 的反馈单独展示，没有猜配。

实际执行了：旧方案 → 新需求 → 第二个明确标记的交互验收任务 → 我的方案回看原任务；保存结果反馈 → 生成新的理解 → 重新搜索推荐 → 回看旧版本及其反馈。完整任务通过原生文件保存对话框导出，文件读回包含 3 个版本、2 条反馈和 1 个原会话关联。再经原生热升级后，两条任务、历史版本、反馈与会话关联仍在。原生「继续原会话」回到准确的旧会话，输入框为空，没有发送新消息。

## 实跑发现后追加修正

第一次本机预览发现：调整意见进入了理解模型，但后续推荐只接收到新的意图，没有接收到已知旧候选失败原因，因此重复推荐了同一个候选。该失败版本保留，未删除或改写。

本版推荐只从所选版本及祖先版本取得有界用户反馈，排除兄弟分支；明确区分用户报告和本轮独立验证。旧候选已报告违反硬条件、又无修复证据时，不得仅凭同一份作者介绍再次强凑单插件方案。反馈提到的其他插件也必须在本轮真实候选内，不能凭反馈添加候选。

修复后沿保存的第二版理解重新推荐，实际形成第 4 版 `native` 方案：明确引用旧候选的已报告冲突及缺少修复证据，不再选择该插件，也没有把本轮未召回的 Obsidian 加入依赖。原三个版本仍在。本轮没有安装新候选或重新执行资料库任务，所以该结果只证明反馈已进入推荐判断。

## 自动检查与边界

完整测试 168/168 通过，构建成功。独立复核覆盖历史、失败清理、过期页面、容量、导出回导、精确会话绑定及反馈进入推荐等路径；最终反馈补丁另有 47 项定向检查通过。

本次是开发者本机验收，不能计作外部用户反馈、插件成功分发或留存。恢复了有备份的这一次方案，不代表能找回任何已删除且无备份的数据。没有重启 Host，因此不把热重载记录称为本版的宿主跨重启验收。推荐仍受来源覆盖、作者资料质量及模型判断限制。
