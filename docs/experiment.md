# 两天小实验：从描述需求到第一次用成插件

要验证的是：已有 DSH 用户描述需求后，Finder 能否让他们更快选对插件、完成第一次任务，并让原本不认识的创作者获得一次有效触达。当前还没有外部用户增长、留存或生态正向循环的结果。

## 已经知道什么

- 三组真实中英文意图已通过生产发现模块在线检索，未把目标插件名放进查询：多格式文档提取、Markdown 图表预览、每日日志月历。
- 对应候选在返回结果中排第 2、1、1；18 个返回候选均在旧的 15 条样本之外。也出现了视觉桥接、数学求解、Token 热力图等噪音，不能只报“搜到了”。
- 这只是动态召回与作者资料核查，不能换算成安装成功、任务完成或真实采用。
- 已有 [dsh-find-plugin](https://github.com/awesome-dsh-plugin/dsh-find-plugin) 提供实时 GitHub topic 搜索、精选库描述补充与降级检索。Finder 要证明的增量是意图理解、候选判断和首次落地。

## 怎么安排两天

目标邀请 6 名已在使用 DSH 的用户，每人做 3 个不同任务，预计每人 45 分钟以内。人数是本次试验目标，尚未完成招募。

比较三种方式：

| 方式 | 用户怎么做 |
|---|---|
| M：手工市场搜索 | 自己在 DSH Discover 搜索、读详情、选择并安装插件，再完成任务。 |
| D：已有发现工具 | 对 dsh-find-plugin 描述需求，按它返回的候选继续选择、安装和使用。 |
| F：本 Finder | 描述同一类需求，经意图确认、候选理解、方案确认，再到宿主安装与首次使用。 |

统一宿主版本、模型配置、空白测试工作区和合成材料；预先检查三种入口是否真的能运行。Discover 使用同一个公开精选索引。发现工具自身的安装与配置耗时另外记录；从选定候选到安装、授权和首用的耗时计入任务。某种入口不兼容就记真实阻断，不能人工代答后当作该工具可用。

每人不重复同一个任务，避免记住插件名字后影响后续比较。采用下面的交叉安排；不提前透露目标插件名。

| 用户 | 第一次 | 第二次 | 第三次 |
|---|---|---|---|
| 1 | A / M | B / D | C / F |
| 2 | A / M | C / F | B / D |
| 3 | B / F | A / D | C / M |
| 4 | B / F | C / M | A / D |
| 5 | C / D | A / F | B / M |
| 6 | C / D | B / M | A / F |

这样每种方式有 6 次计划尝试，每个任务在每种方式下有 2 次。参与者基础差异、样本量和学习效应仍需保留，结果按原始次数报告，不做显著性或总体转化率结论。

第一天完成入口检查、材料准备和前 3 人试用；修复只阻断试验的错误并记录版本。第二天完成其余 3 人、核对结果和归纳卡点。若中途改动推荐或交互，前后版本分开报告。

## 三个任务与完成标准

| 任务 | 给用户的需求 | 可核对的完成标准 |
|---|---|---|
| A：多格式提取 | 把测试目录里的 PDF、Word、Excel 和 PPT 内容转成 Agent 可读的文本，尽量本地处理。 | 四份合成文件都得到可读结果，事先埋入的关键文字或表格值没有漏掉；只预览文件不算完成文本提取。 |
| B：Markdown 预览 | 在 DSH 右侧看这份 Markdown 的 Mermaid 流程图和数学公式，并能查看图表源码。 | Mermaid 变成含正确节点文字的 SVG，可切换源码再返回；公式仍正确。原生已支持 KaTeX，增量只记 Mermaid 图形与交互。 |
| C：每日日志 | 记两条当天记事和一条待办，在月历里找回，完成待办后刷新还能看到。 | 条目与日期正确、月历可定位、待办状态修改持久保留。只有提醒或 Token 日历不算完成。 |

不用预定插件名判胜负；其他候选只要满足同一完成标准也可以。每个任务最多 15 分钟。原生能力已经够用时，允许选择不装插件，并记录理由；不能为了“转化”强推安装。

## 记录什么，怎么算

一次“尝试”从用户拿到需求、入口可用并开始操作计时，直到完成、放弃或 15 分钟结束。全程只用合成材料。原始记录使用匿名用户 ID，不收集凭据、私人会话或业务文件。

| 指标 | 定义与分母 |
|---|---|
| 意图准确 | 用户确认目标、输入、输出及约束无关键遗漏；`准确次数 / 已开始尝试数`。记是否补问、改了哪里。 |
| 合适候选 | 用户最终选中的候选，经独立按文档核对能够覆盖任务，且已知平台、账号、版本前提满足；`选到合适候选次数 / 已开始尝试数`。另记误选、无结果和原生已足够。 |
| 安装成功 | 宿主回读到精确包与版本，启动后实际加载；`成功安装次数 / 用户确认安装次数`。下载完成或点了安装不算成功。无需安装单列。 |
| 首次任务成功 | 产物或界面满足上表标准；主口径为 `成功次数 / 已开始尝试数`，另报 `已安装并首用队列中的成功次数 / 已成功安装并实际首用次数`，避免把前段流失藏起来。原生够用而无需安装的成功单列，不混入后一个分子。 |
| 时间 | 分开记需求确认、候选选择、安装、首用和总耗时。成功任务报告中位耗时；失败保留实际耗时与原因，超时按 15 分钟结束，不能从时间统计中无声删除。 |
| 新创作者有效触达 | 用户自报此前不认识该仓库维护者，本轮主动打开其详情或 README；`发生触达的尝试数 / 回答过认识与否的尝试数`。同时报答复覆盖率。维护者命名空间不等于独立自然人。 |
| 触达到实际价值 | 对此前未见过的维护者，分别记确认安装、安装成功、任务成功的次数；只点开不算采用，不据此推作者收入或持续曝光。 |

每次记录：方式与版本、任务、意图修正、搜索来源及可用状态、候选与选择理由、精确安装来源、各阶段时间、首次结果证据、是否认识维护者、最大卡点。用户自报“成功”和实际完成标准冲突时，两者都留存。

失败分成意图理解错、搜错或漏掉、来源不可读、版本／平台／账号不满足、安装失败、不会开始用、运行失败、结果不合格、主动放弃。搜索超时或源失败不能写成“没有插件”；部分完成与完全失败分开。主持人需要接管时记录接管点，该次不能算独立完成。

## 两天后据什么决定下一步

逐任务对照三种方式：Finder 有没有少走弯路、减少误选、提高首次成功，代价是不是更多确认和等待。再看是否让原本不认识的维护者获得了实际安装或任务完成。

- 若只让人更快搜到名字，后面仍不会用，优先补首次使用指引与方案交接。
- 若候选里经常混入同词不同事的插件，先修任务匹配与反例判断。
- 若安装与兼容阻断最多，先改善前提识别和宿主交接。
- 若已有工具与手工搜索同样顺畅，保留这个结果，收窄到确有增量的任务。

公开结果只报实际参与人数、尝试次数、阶段流失、耗时和具体案例。这次能验证的是任务链路中的局部增量；增长、复用和生态正向循环需要后续观察。
