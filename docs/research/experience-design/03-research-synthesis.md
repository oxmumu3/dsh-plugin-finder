# Finder 体验设计研究综合

核查日：2026-10-23。依据：主任务当日保存的一手网页正文 JSON；本轮通读其正文后综合，未新增网络采集、用户访谈或可用性测试。以下验收均为待执行标准，不是已通过结果，也不证明转化率、效率或留存已经提高。

## 结论与使用方法

Finder 应围绕“说出需求 → 判断可复用办法 → 核对并继续 → 必要时共创”组织体验。自然语言负责表达与修正，结构化界面负责看清方案、比较前提和执行确定动作；视觉与品牌让这一过程有清楚的重心和可信的态度。研究并不支持把全部操作改成聊天，也不支持给旧表单换一套颜色就宣称体验完成。

本报告把不同证据分开使用：NN/G 提供研究解释和实践判断，Microsoft HAX 提供基于研究综合的 AI 交互指南，USWDS 与 Design Council 提供设计原则和过程框架，Ant Design X 提供行业提出的 AI 界面范式，AI SDK 与 assistant-ui 提供实现路径，W3C 提供具体无障碍条款的解释。它们不能互相代替，更不能直接证明 Finder 的效果。

后续独立补充只读核验了Ant Design X与assistant-ui的固定版本源码及许可证，见 [开源实现参考](05-open-source-patterns.md)。下表的网页阅读范围保持原样，不将后续源码抽查扩大成全库审计。

本地问题对应 [01-local-audit.md](01-local-audit.md)。家庭助手截图只作视觉质量参考；用户对视觉的认可不能扩张成交互认可。

## 1. 先定义要改善的任务，再选视觉与组件

- **一手结论：** Design Council 的双钻石先理解问题、再定义挑战、探索答案并小规模检验；USWDS 要求从真实需要出发，以原型检查假设，并持续观察使用情况。[S1][S2]
- **适用边界：** 这是过程框架，不是必须走完四个审批阶段的流水线。源码审计、竞品阅读和 Agent 自测能发现问题，但不能冒充真实用户研究。
- **Finder 具体改法：** 先固定三个任务：不知道有什么时发现可尝试的用途；已有需求时得到有依据的办法；结果不合适时修正或共创。用这三个任务裁决首页内容、结果层级与共创入口，不因多了一个功能就新增 tab。先比较两种组织方式，再实现一个可检查方案。
- **可观察验收：** 每项首屏内容都能说明服务哪个任务；同一产品不在推荐和精选中重复占位。用固定任务脚本记录找到下一步、理解前提、退出恢复和错误恢复的实际过程；视觉评价与任务表现分开记录。未来若进行用户测试，单独记录参与者与范围。

## 2. 逐步展开的是次要复杂度，不能藏起关键判断

- **一手结论：** NN/G 将渐进呈现用于把高频核心能力与低频高级能力分开；入口必须清楚，用户能预期展开后会看到什么。文章同时区分逐步呈现与线性向导：频繁相互调整的内容不宜拆成来回跳转的步骤。[S3]
- **适用边界：** “少显示”不是目标。安装前提、来源失败和关键限制若影响是否继续，就必须在决策时可见。也不能从文章推出“任何页面都只能有两层”这样的绝对规则。
- **Finder 具体改法：** 结果顶部显示推荐路径、为何适合、最重要的前提与下一步；来源细目、完整版本、检索统计进入有明确名称的展开区。修改需求与比较方案留在同一任务上下文；工作区选择和安装操作在实际需要时出现。共创蓝图默认可读，按块编辑，完整技术字段置于高级编辑。
- **可观察验收：** 首次结果视图不必先滚过完整安装说明就能找到下一步；展开入口能让人预期其内容。关键失败、额外权限和无法安装的前提不只藏在详情里。展开、修改与返回后，原请求、选择和编辑均保留。

## 3. 用高对比层级服务任务，视觉认可与可用性分别验证

- **一手结论：** NN/G 指出美观会影响感知易用性，并可能掩盖任务困难；重大交互问题不能靠视觉弥补。USWDS 要求内容有逻辑顺序、主旨易懂，并把颜色对比纳入设计。[S4][S2]
- **适用边界：** NN/G 文章是研究解释与案例总结，文中历史实验并非本轮读到的原始论文。它不证明某一种颜色、字号或卡片样式对 Finder 最有效；高对比也不意味着所有内容同样深、同样粗。
- **Finder 具体改法：** 建立一个视觉焦点：首页是任务输入，结果页是判断与主动作，共创页是当前蓝图。正文、辅助说明、状态与交互有稳定层级；次要信息通过位置、字号和展开关系降级，避免靠低对比小字隐藏。颜色承担动作或状态语义，装饰不挤占任务空间。
- **可观察验收：** 1440×1000 与 390×844 下分别截图，检查焦点、文字、重叠与滚动；去掉颜色后仍能辨认推荐、警告和主动作。列出正文、辅助文字、状态、按钮、焦点的实测颜色对比值，按实际采用的无障碍条款另行校验。视觉通过不能代记任务通过。

## 4. 先明确产品角色，再保持品牌的一致表达

- **一手结论：** Ant Design X 的 RICH 范式把角色、意图、会话和混合界面作为 AI 设计的关注要素；角色用于匹配用户期待。Mailchimp 的官方写作规范把稳定表达与清楚、体谅用户的解释方式联系起来。[S5][S6]
- **适用边界：** RICH 是企业团队提出并在行业实践中迭代的范式假设，不是经本轮独立验证的普遍定律。Mailchimp 的品牌人格也不应直接移植到 Finder。
- **Finder 具体改法：** 角色定位为“帮你判断能用的办法，必要时一起形成可交付的插件蓝图”。稳定特质为清楚、可靠、愿意一起动手；避免官方审核者、万能代办者或只会展示目录的商店口吻。界面文案、结果解释、策展卡和 Creator 交接都保持同一角色，明确各自能做到哪一步。
- **可观察验收：** 对首页、候选、失败、共创、交接各抽取一段文案，能说明其共同角色。来源核对不写成质量认证，准备草稿不写成执行完成，进入 Creator 不写成插件已建好。视觉系统与角色相符，但不以头像或拟人装饰代替能力说明。

## 5. 品牌表达稳定，具体语气随情景变化

- **一手结论：** Mailchimp 区分相对稳定的 voice 与随对象情绪和情景调整的 tone，并优先清楚表达。NN/G 用幽默、正式程度、尊重程度和情绪热度四个维度分析语气；文中研究观察的是读者印象差异。[S6][S7]
- **适用边界：** NN/G 文中在线调查来自 50 名美国受访者，不能直接推论中文 Finder 的偏好、任务完成率或转化。轻松不等于总要开玩笑，错误和权限情景更需要准确。
- **Finder 具体改法：** 首页用自然邀请，方案用简短具体的判断，共创用协作口吻；失败时平静说明发生什么、内容是否保留、下一步是什么。采用“部分来源没有读完，先重试看看”这样的准确说明，避免“什么都没找到”“马上搞定”“Oops”或责怪用户的表达。按钮写实际动作，例如“准备会话草稿”“保存蓝图”。
- **可观察验收：** 为欢迎、等待、无充分候选、来源失败、保存失败、交接完成各准备一条情景文案，逐条检查事实、动作和语气。即使不看颜色与图标，也能知道状态与可执行的下一步；成功语气不超出回执证明的范围。

## 6. AI 的能力、误差与不确定性应在需要时可见

- **一手结论：** HAX 要求说明系统能做什么及其可靠程度；不确定时缩小服务或澄清，并让用户能够理解系统行为及行动后果。官方指南页把这些建议描述为长期研究的综合。[S8][S9]
- **适用边界：** 本轮读到官方指南及 18 条释义，没有重读其 CHI 论文、验证样本或逐项设计案例；这些指南不意味着模型建议已经正确，也不等于要在首页堆满免责文字。
- **Finder 具体改法：** 首页一句话说明使用宿主模型找办法、不会自动安装或执行。结果区分原生可做、现成插件、组合与待补缺口；来源失败、过期缓存和安装/任务未验证在相关判断旁说明。等待时显示真实阶段和原请求，没有事件支持就不画百分比或假来源进度。
- **可观察验收：** 模型未配置、实时成功、部分失败、过期缓存、无充分候选各有独立状态；来源失败时不会生成“生态没有供给”的结论。对原生方案、公开包、预览案例、私有接入分别检查能做的下一步。原型的搜索、模型与安装演示均显式标注。

## 7. 让纠正、取消和恢复成为主流程的一部分

- **一手结论：** HAX 强调容易调用、容易退出、有效纠正，以及记住近期交互；USWDS 的连续性原则要求支持离开后返回和复用已保存信息。[S8][S2]
- **适用边界：** 记住当前任务不等于允许跨项目读取全部历史。更自动化也不等于静默覆盖草稿；能取消界面等待不表示已经撤回服务端已发生的动作。
- **Finder 具体改法：** 用户在结果或蓝图旁补一句，修改同一任务并保留原话与版本；已有信息不重复问。搜索期间保留请求和上一份结果，取消后可继续编辑。普通草稿被宿主保留、Creator 已建但关联保存未知等情况分别提供恢复路径，避免重复建会话。
- **可观察验收：** 连续演练“补一句→更新→回看旧版”“取消→重新提交”“超时→重试”“离开→恢复”。迟到响应不覆盖新输入，未保存编辑可恢复，已有草稿不被覆盖。未知结果保留未知，恢复入口不会重新发送任务或重复创建已知会话。

## 8. 反馈与个性化要给用户可理解的控制

- **一手结论：** HAX 要求细粒度反馈、谨慎适应、告知行动后果和全局控制；USWDS 将可靠、透明、妥善管理用户数据与持续听取反馈作为信任基础。[S8][S2]
- **适用边界：** “学习用户”不是新增遥测的授权；用户自报完成也不是运行验证。为了改进推荐而收集的摘要不能在界面中被描述为无需隐私判断的匿名数据。
- **Finder 具体改法：** 推荐理由只引用允许使用的本机信号，可减少推荐、恢复设置。任务反馈随试用结果回到原方案，可指出具体卡点；是否用于模型优化、是否回传分别表达。共创与私人历史继续遵守现有本机边界，不把个性化变成开始使用前的问卷。
- **可观察验收：** 冷启动不出现伪造的“为你推荐”理由；关闭回传仍能完成查找与保存。用户能区分本机保存、等待同步、服务端确认和删除待处理；细粒度反馈不会覆盖原始结果证据，设置关闭后不自动补传旧记录。

## 9. 对话负责表达，结构化卡片负责看清与操作

- **一手结论：** Ant Design X 用混合界面承接输入、生成和结果应用；AI SDK 的官方实现文档展示将工具返回数据渲染成 React 组件，并区分等待、输出与错误。assistant-ui 概览也把界面组件与连接后端的 runtime 分开。[S5][S10][S11]
- **适用边界：** 这些是行业范式与工程实现资料，不是“聊天必然更好”的研究证据。AI SDK 示例使用模拟天气与股票数据；assistant-ui 本轮只读概览，未审核其具体 API、可访问性、依赖或许可证。研究没有要求 Finder 更换技术栈。
- **Finder 具体改法：** 保持自然语言入口，结果转成受控的方案卡、前提卡、比较卡、蓝图卡；确定动作继续使用按钮、选择器和局部编辑。组件从经过验证的数据结构渲染，动作绑定任务/版本/工作区；模型文本不能直接变成任意 HTML、安装命令或已执行状态。复用现有 React 与宿主服务前先核对契约。
- **可观察验收：** 同一份任务数据在对话解释与结果卡里一致；等待、错误和可用输出不共用一个成功外观。自由输入、版本切换、原生草稿保留与 Creator 接续都能走通；仅模拟的卡片动作明确标记。选择候选后要重新评估方案，不能只换“已选中”标签。

## 10. 精致感不能以更难点击、更难阅读为代价

- **一手结论：** W3C 的 2.5.8 解释页要求指针目标至少为 24×24 CSS 像素，或满足规定的间距等例外，并指出更大目标对很多人有帮助。USWDS 将键盘、辅助技术、逻辑顺序与可读内容作为整体设计责任。[S12][S2]
- **适用边界：** 24×24 是该条款的尺寸要求，不是所有目标的推荐上限；行内文字链接等有具体例外。该页不能证明文本对比度、焦点或整个产品符合 WCAG，桌面截图也不能代替键盘检查。
- **Finder 具体改法：** 主要操作有舒适点击区域，辅助操作不缩成难点的小字；状态配明确文字，键盘焦点可见。窄屏保留输入、结果与下一步，辅助信息进入展开区。抽屉和弹层处理焦点、Escape 与返回，动效不阻挡阅读和操作。
- **可观察验收：** 检查按钮、标签、展开入口和关闭控件的实际命中区域；低于 24×24 的逐项验证适用例外，不凭视觉猜测。用键盘完成核心路径并检查焦点顺序；390×844 无横向溢出，缩放后内容与动作不互相遮挡。对比度、读屏和减少动效另行检查并记录实际范围。
